## 32a. Correction — September 18, 2026: the session-persistence issue was real and has been fixed architecturally

The pre-warming experiment above correctly identified the *trigger* (module instantiation timing) but the wrong *fix* (documenting it away). The actual defect: `BuildService` kept `analyze()`'s output in a process-local, module-scoped `Map<string, StoredSession>`, keyed by a `planId` the browser echoed back on `search()`. That map is only ever reliable when both requests land in the same running module instance holding the same object. Next dev's on-demand per-route compilation was simply the easiest way to observe that this precondition can fail — the identical failure mode would recur in any real deployment where `/api/build/analyze` and `/api/build/search` are not guaranteed to hit the same worker process (separate serverless invocations, separate Fluid Compute/Function instances, a restart between the two calls). The bug was in relying on shared in-memory state across two independent API requests at all, not in dev-server tooling.

**Fix — stateless, signed Build session token.** `analyze()` no longer stores anything server-side. It signs the validated `BuildAnalysis`, `BuildConstraints`, `source`/`fixtureName`, `usage`, owner, and an expiry into an opaque HMAC-SHA256 token (`BuildSessionSigner` in `src/lib/server/build-session-token.ts`) and returns it to the browser as `session.token`. `search()` takes that token back, verifies its signature and expiry, checks the owner claim against the caller's own session cookie, and only then reconstructs `analysis`/`constraints` from the verified payload — never from a lookup keyed by anything the client sent. The plan (and therefore budget allocation, inclusion, and each `ProductIntent`) is recomputed fresh from that verified data plus the caller's `selectedIds` on every call; a `selectedIds` entry that doesn't match a real, signed component id is silently ignored, not trusted into a plan item. Because the token is signed, not encrypted, and never contains image bytes or a secret, tampering with any field (budget, a component's role, `existingItems`, etc.) invalidates the signature and is rejected with `BUILD_SESSION_INVALID`; a token replayed by a different browser session is rejected with `BUILD_SESSION_EXPIRED`; an expired token (15-minute TTL, same as before) is rejected the same way. `priorResults` lets the caller echo back its own previously-found products so a stateless server can still return one complete, accumulated view — this is opaque display data only, never trusted for pricing, ownership, or search decisions.

**Why this works across route/process boundaries.** The token itself carries everything `search()` needs, so no two requests ever need to share an object, a module instance, or a process — this is the same reason Request Mode's own multi-step flow never hit this class of bug. The one thing that *does* need to be consistent across processes is the signing secret, and that's handled the same way the existing AI budget ledger handles its own cross-process durability need: `SENTINEL_BUILD_SESSION_SECRET` (a real env var) is used if set — the correct answer for a genuine multi-instance deployment, since it's shared config, not shared memory — and otherwise a secret is generated once and persisted to `.sentinel/build-session-secret` (same directory, same atomic-create-once pattern as `ai-usage.json`), so it survives dev-server restarts, Fast Refresh module reinitialization, and multiple processes sharing one machine's filesystem. Verified directly: two independently constructed `BuildSessionSigner` instances pointed at the same directory (simulating two separate worker processes with no shared object graph) sign with one and verify with the other successfully (`build-session-token.test.ts`); the equivalent is proven for `BuildService` itself in `build-service.test.ts`'s "fresh server/module context" test. Live, over real HTTP against a running dev server with the fixture: 8 consecutive fresh analyze→search round trips (new cookie jar, new token, no pre-warming, each in its own `curl` process) succeeded on the first attempt every time; a tampered token and a token replayed from a different cookie jar were each correctly rejected with 409.

## 32b. September 18, 2026: the live multimodal test (see 33) found a real component-modeling bug, fixed at the architecture level

The one live Build Mode test recommended in item 33 ran against a real photo: a compact wooden computer desk with an integrated pull-out keyboard/work shelf and a lower storage compartment, plus a separate black folding chair. The model correctly understood the overall scene but classified the keyboard shelf and storage compartment as their own separate `RECOMMENDED` purchasable components — they would each have gotten a budget allocation, a selection checkbox, and their own Agnic search, as if they were products sold on their own.

**Root cause:** the component model had only one axis, `role` (ESSENTIAL/RECOMMENDED/OPTIONAL/DECORATIVE) — a priority signal, not a purchase-structure signal. Nothing in the schema or the prompt distinguished "a standalone thing you'd buy" from "a feature that's physically part of something else," so a visibly integrated feature had no way to be represented except as if it were its own product.

**Fix:** added a second, orthogonal axis, `componentKind` (`PURCHASABLE` | `INTEGRATED_FEATURE` | `ACCESSORY` | `DECORATIVE`) and `parentComponentId` to `buildComponentSchema` (`src/lib/domain/build.ts`). `createBuildPlan` now filters to `purchasable = components.filter(c => c.componentKind !== "INTEGRATED_FEATURE")` before doing anything else — plan items, budget weighting, default selection, and dependency edges are all built only from that filtered set. An `INTEGRATED_FEATURE` component therefore never gets a plan row, a budget allocation, a checkbox, or a search, and any dependency edge naming one is dropped (it would never have its own search result to verify against). Its name and `inferredRequirements` are instead folded into its parent's own `ProductIntent` via `integratedFeaturesOf`/`buildProductIntentFromComponent` — a desk with a built-in keyboard tray searches for `"computer desk with pull-out keyboard/work shelf"`, one product, not two. `analyzeBuildScene`'s instructions (`src/lib/server/adapters/openai.ts`) now dedicate STEP 2b to exactly the question the fix needed: "is this object independently purchasable in the intended build, or is it visibly part of another object?", with the desk-drawer/keyboard-tray/monitor-arm examples given for this fix.
